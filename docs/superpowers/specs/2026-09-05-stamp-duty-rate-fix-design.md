# 卖出印花税兜底值 0.0001 → 0.0005

> 状态：已实施并 A/B 实跑验证。
> 日期：2026-09-05

## 场景

回测报告的成本行显示「卖出印花税 0.01%」。A 股卖出印花税是**给国家的税**，
现行税率 0.05%（2023-08-28 从 0.1% 降下来的），不是万1——没有任何券商账户能谈到
这个价，所以这不是"低费率账户"的设定，是笔误。

## 问题

同一个默认值在两个地方各写了一份，且两份不一样：

| 位置 | 值 |
|---|---|
| `domain/backtest/config.py:32` `CostConfig.stamp_duty_rate_sell` | `0.0005`（注释写明现行税率） |
| `app/services/backtest_service.py:103` `_build_config` 的兜底 | `0.0001` |

关键在于**正确那份是死代码**：`_build_config` 永远显式传 `CostConfig(...)`，
所以任何经服务提交的回测都拿不到 dataclass 默认值，实际生效的一直是 0.0001。
`execution.py:68` 的公式 `stamp_duty = amount * costs.stamp_duty_rate_sell` 本身没错，
买入侧不收印花税也是对的。

后果：所有真实回测的卖出成本少收 4bp，收益被系统性高估约 4bp；同时域内测试
直接 `BacktestConfig()` 用的是 0.0005，与生产跑的口径不一致——同一段成本代码，
两边算出来的钱不同。由 `9e8c41f0`（2026-07-10）引入。

## 决定

**兜底值保留**（`_build_config` 显式列出默认费率是可读的，不打算改成"缺省交给
dataclass"那种隐式写法），但值要用真实的那个：`0.0005`。
漂移风险由一条参数化测试钉住，而不是靠"只留一处定义"。

## 实现

`backtest_service.py:103`：`cost.get("stamp_duty_rate_sell", 0.0001)` → `0.0005`。一行。

新增 `tests/app/test_backtest_cost_defaults.py`：

- `test_build_config_cost_fallback_matches_dataclass_default`：对 `CostConfig` 的
  **全部 6 个字段**逐一断言 `_build_config({})` 的兜底 == dataclass 默认。
  这条测试就是防止再次漂移——以后再改任何一处都会红。
- `test_stamp_duty_matches_current_a_share_rate`：直接钉 0.0005 这个真实值。
- `test_request_override_still_wins`：兜底没把覆盖能力吃掉，自定义费率（如低佣金账户）
  仍可传入，未覆盖的字段仍走默认。

## 验证

同一次选股（`20260821_061254_selection_37edc9ec`，96 笔）跑两遍，只差印花税：

| | 0.0001（旧） | 0.0005（新） | 差 |
|---|---|---|---|
| Σ盈亏 | −51,659.91 | −53,279.21 | −1,619.31 |
| Σ卖出名义 × 4bp | | | 4,048,263.19 × 0.0004 = **1,619.31** |
| pnl_return_pct | −1.2609% | −1.3004% | −0.0395pp（=4bp） |

差额与理论值精确到分吻合，笔数不变（96 = 96，没有多算或少算交易）。
`GET /api/backtest-results` 的 `trade_rule.costs.stamp_duty_rate_sell` 现在是 0.0005，
前端成本行随之显示「卖出印花税 0.05%」（前端零改动）。

全量 `.venv/bin/pytest -q`：518 passed（+8）。

## 影响：历史产物是高估的

**已经落盘的报告不会自动更新**。此前所有经服务提交的回测，收益都高估约
4bp/回合（买入一次卖出一次共承担一次卖出印花税）。要正确的数就得重跑；
`2026-08-17 ~ 2026-09-03` 那份全市场实跑的 Σ盈亏按 4bp × Σ卖出名义 约需下调 7 万元
（填坑战法一组：投入名义 1.767 亿 → 70,680 元，约占其 Σ盈亏的 1.8%）。
